# MaxTravel live UX audit — 16 November 2026

Verdict: the core one-way flight and hotel checkout paths work through review, but this is not a launch-readiness sign-off. Several customer-facing failures and recovery problems remain.

## Method and limits

Live visual/functional checks used Chrome and the existing authenticated in-app browser session on maxtravel.in. Desktop views were 1920 and 1280 pixels wide; mobile views were 390 pixels, with an additional 320-pixel admin check. Mobile checks are responsive browser checks, not physical iOS/Android testing. No load generator, payment submission, supplier booking, refund, cancellation execution, or live pricing-rule save/deactivation was performed.

The user authorised one temporary INR 10 promo, AUDITNOV16. It was created, applied to both products, removed from both quotes, disabled, and its disabled rejection verified. The disabled row remains as audit history. All browser viewport overrides were reset. Synthetic traveller/document entries were used only before payment; no saved traveller was created.

This audit does not establish that every possible route, airline, supplier, date, fare, currency, party size or failure mode works. Payment-provider opening and paid fulfilment were not retested in this session. International, multi-city, multi-room, child/infant and corporate-specific bookings need additional coverage. The authenticated account had no trips, so voucher download, existing-booking details, cancellation and refund journeys could not be exercised from its customer workspace.

## Findings, prioritised

### P1 — Packages cannot load

The live /packages page displayed “We couldn’t load packages.” A single Try again repeated the failure. Its Browse packages recovery link points back to the same failing page. Customers cannot browse or select a package.

Source inspection: the catalogue adapter fetches the fixed CRM public package endpoint and maps upstream/network/schema failures to 503. Browser evidence does not establish which of those causes occurred. Check CRM endpoint availability and payload contract from the app container, retaining sanitised diagnostics; avoid silently masking an outage as an empty catalogue.

### P1 — A selectable hotel rate fails at review with generic recovery

Fabhotel Ssr Fern Suites, Executive Room / Breakfast, INR 2,651.37 showed availability and a free-cancellation deadline. Continue with room returned “We could not complete your request. Refresh availability or contact MaxTravel.” The customer is left on the room/property screen without a specific explanation or a prominent dedicated retry for this failed review.

Another property reviewed successfully, so this is not evidence of a universal hotel outage. Correlate this request with sanitised server/supplier logs before attributing the cause. Keep the selected property/rate and expose explicit Refresh rooms / Choose another stay actions.

### P1 — Flight checkout reload silently loses progress

Reloading the flight Review & pay screen returned to the initial search form. Dates/route survived; fare selection and entered traveller details did not. Unlike the hotel path, no explanatory recovery notice appeared. A customer can reasonably believe the booking has disappeared.

Restore a safe selection/review handoff where possible, or clearly explain what was cleared and offer a one-click search recovery. Do not store sensitive document data in URLs or unprotected persistent browser storage to solve this.

### P2 — Non-refundable hotel refresh produces a noisy terms-change warning

For Hotel Lake View Airport Zone, refreshing the reviewed price preserved INR 2,708.78 but showed “1 reviewed detail has changed” and a large comparison panel. Only the first cancellation interval start moved from 16 Nov 17:17 to 17:18 IST; future boundaries and amounts stayed identical.

Source inspection confirms the existing equivalence helper only normalises the currently active **free/refundable** window. This non-refundable paid window falls outside that handling. Extend comparison only with a validated semantic rule that preserves genuinely changed future fees, thresholds, refundability and missing-data warnings.

### P2 — Connecting flights lack useful total duration and repeat itineraries

Several AI Express connecting results displayed “Total duration unavailable.” The same visible segment/time combinations appeared on separate cards with different fare groups. This makes comparison and the “shortest” choice less useful. Do not simply add airborne durations and omit layovers, or deduplicate supplier offers that have different compatibility constraints. Derive elapsed time only from reliable airport/timezone data and consolidate display groups while preserving offer identity.

### P2 — Promo recovery wording is misleading for definite rejection

An unknown code says “Apply or remove the code again to confirm your total before paying,” although the failure is a definite not-found response and the unchanged pay button remains enabled. Separate definitive rejection from network/unknown outcome. Source inspection also found no client timeout in CheckoutPromo's fetch, which can leave the busy state waiting on a stalled connection; this stalled-network case was not reproduced against the live VPS.

### P3 — Admin empty state and narrow modal polish

Before creating the test code, the promo page had no “No promo codes yet” empty state. The 320px pricing editor showed nested vertical scrolling and a small horizontal scrollbar (dialog client width 254px, scroll width 256px). No control was proven inaccessible, but the layout needs polish. Internal UUIDs dominate the modal header/intro where a human-readable product/audience label would be clearer.

### P3 — Duplicate destination labels

Hyderabad suggestions contained two identically labelled “HYDERABAD, TELANGANA, INDIA” choices, plus district and Pakistan alternatives. Users cannot distinguish the identical choices. Consolidate only genuinely equivalent destinations or display a useful differentiator.

## Remediation (16 November 2026)

- Flight checkout now saves only its validated public selection in the existing account-bound, expiring handoff. Reload restores the selection with an explicit current-price action and explains that private traveller details must be entered again. Pending payment recovery remains authoritative and blocks a second checkout.
- Hotel review rejection now offers refreshing room options or returning to stays with the search retained. The supplied VPS log establishes HTTP 400 / supplier code 6001, not its underlying meaning. No automatic booking or payment retry is introduced.
- The cancellation comparator accepts a moving origin in an already active non-refundable window only when refundability, all amounts, future boundaries and subsequent origins remain identical. Worker comparison still preserves every other raw policy field.
- Flight elapsed times use existing IANA airport data and retain fail-closed handling for unknown/ambiguous times. Identical segment payloads share a card while preserving distinct fare IDs and compatibility data; conflicting same-ID offers stay separate.
- Promo requests time out after 15 seconds. Definite rejection retains the current total; ambiguous failures block payment until a successful apply/remove confirms the total. Empty promo lists explain how to create the first code.
- Pricing dialogs fit 320px, use product labels instead of prominent UUIDs, and retain access to all controls. Duplicate destination labels identify separate hotel collections instead of silently discarding supplier region IDs.
- Package failures have a useful trip-planning/contact route instead of linking the list back to itself. **Upstream dependency remains:** the public CRM catalogue currently redirects to login. The latest MaxTravel CRM source contains the public route; its deployed version/proxy must be corrected separately. The booking application must not follow a login redirect or fabricate package inventory.

Browser verification uses the production build with synthetic provider responses; it does not establish production supplier availability or load capacity. The temporary live audit promo remains disabled. No real payment, booking or production pricing change is part of remediation.
